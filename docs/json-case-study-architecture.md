## 1. Критический разбор v1 (саморецензия)

### Что было хорошо

1. **Разделение WHAT / HOW** — JSON описывает контент и выбор компонента, компоненты — внешний вид. Соответствует `architecture.md` и `ai-philosophy.md`.
2. **CaseRenderer ≈ 40 строк** — тонкая карта «component name → React component», без нового слоя.
3. **`content` маппится 1:1 на реальные пропсы** существующих организмов (проверено по коду во время ревизии).
4. **AssetResolver** — минимально необходимая абстракция для сериализации `ReactNode`-пропсов (`image`, `icon`).
5. **Unknown `type` → dev-warning, не краш** — защита от опечаток без потери прод-стабильности.

### Что было слишком сложно / не нужно

1. **Поле `type: "hero"` вместо точного имени компонента.** Создавало отдельный слой наименований: JSON-имя ≠ Figma-имя ≠ React-имя. Нужна таблица соответствия, и она будет дрейфовать при переименованиях в Figma. **Упрощение:** убрать `type`, использовать точное имя `component: "HeroSection"` (одно имя на все слои).
2. **Глобальная «union всех секций»** — v1 не показала, что делать с новыми секциями. Если union статический, каждый новый компонент = правка типа. **Упрощение:** типизированная карта `ContentMap` (component name → тип пропсов), дополняется точечно; рендерер строится на ней же.
3. **Игнор композитных секций.** В кейсе есть блок №8 «MVP growth» = `PersonaSection` + `RolesTable` + `CommonCard` в общих обёртках (`.mvpSection` / `.gapMapBlock` / `.gapCardSlot`). v1 не отвечала, как это сериализуется, а значит «новый кейс = новый JSON» ломался бы на первом же таком блоке. **Решение:** механизм `blocks[]` — рекурсивный список компонентов внутри секции.

### Что станет больно после 5–10 кейсов

1. **Дрейф имён и node-id.** Без обязательного `figmaNode` на каждой секции «сверка с Figma» превращается в ручной поиск узлов. **Решение:** `figmaNode` — обязательное поле; образы тоже получают `figmaNode`.
2. **Случайные имена изображений.** Без конвенции AI генерирует `image_final_v2.png`. **Решение:** предсказуемая конвенция имён + одна папка на кейс (см. §4).
3. **Композитная вложенность.** Глубокие вложенные фреймы Figma не переносятся в «плоский» список секций. **Решение:** `blocks[]` с ограничением глубины 1 (сегодня достаточно), более глубокая вложенность → новый организм (правило `design-system.md`: extract reusable patterns).

### Где может упасть AI-генерация

| Риск генерации | Защита |
|---|---|
| AI пишет `component: "Hero"` или `"heroSection"` вместо `"HeroSection"` | Типизированная карта + dev-warning на неизвестное имя. TS ругается на опечатки |
| Неверный `figmaNode` (перепутал узел) | Проверка в workflow «сравни component с node»; node-id копируется AI напрямую из Figma-дерева |
| Неверное значение варианта (`"info"` вместо `"insight"`) | Union-типы вариантов в `ContentMap` — compile-time ошибка |
| Ломаный JSON (длинный текст, кавычки, `\n\n`) | JSON.parse + `validate`-утилита на dev; Storybook-стори кейса рендерит JSON на старте |
| Выдуманный путь к изображению | Конвенция имён + резолвер, который при отсутствии файла рисует плейсхолдер |

### Итог ревизии

Идея v1 верна (WHAT/HOW, тонкий рендерер, AssetResolver). Исправляются: именование (точные имена), обязательный `figmaNode`, `blocks[]` для композитов, конвенция изображений. Убираются: лишний слой `type`, статическая глобальная union.

## 2. Обновлённая архитектура

Принцип не меняется:

```
JSON описывает ЧТО рендерить.
React-компоненты описывают КАК это выглядит.
```

Пайплайн:

```
content/cases/<slug>/case.json
        ↓
CaseRenderer (src/entities/case) — реестр + рекурсивный рендер
        ↓ switch по component
Section Components (существующие organisms / molecules — без изменений)
        ↓
UI Components (atoms — без изменений)
```

Правила:

1. **В JSON только:** контент, выбор компонента (`component`), маппинг на Figma (`figmaNode`), ссылки на изображения.
2. **Никаких** CSS-значений, spacing, цветов, типографики, layout-значений в JSON.
3. **`component` = точное имя Figma-компонента** (PascalCase). Оно совпадает с React-экспортом и Storybook-именем. Один нейминг на все слои.
4. **`figmaNode` обязателен** на каждой секции и на каждой ссылке на изображение.
5. **Неизвестный `component`** → dev-warning (консоль/Storybook), но никогда не роняет прод.
6. **Секции оборачивает CaseRenderer** (стандартная обёртка секции, токенизированный отступ). Модификаторы страницы (`sectionLeft`) переносятся в компоненты или остаются в слое страницы, но не в JSON (см. §7, пункт 4).
7. **`schemaVersion` обязателен** в корне документа — номер ревизии схемы. Рендерер проверяет поддержку версии и предупреждает при несовпадении.

## 3. JSON Schema v2

```jsonc
// content/cases/acquiring/case.json
{
  "schemaVersion": 2,                    // number — ОБЯЗАТЕЛЬНО. Номер ревизии схемы
  "site": "case",                        // string — тип документа
  "slug": "acquiring",                   // string — роут-параметр
  "meta": {                              // object — метаданные страницы
    "title": "...",                      // string — <title> / og:title
    "description": "..."                 // string — meta description
  },
  "sections": [                          // array — порядок страницы в Figma
    {
      "component": "HeroSection",        // string — ОБЯЗАТЕЛЬНО. Точное имя Figma/React/Storybook-компонента
      "figmaNode": "1799:6225",          // string — ОБЯЗАТЕЛЬНО. Node id узла в Figma
      "key": "hero-intro",               // string? — опциональный стабильный id (отладка / якоря)
      "content": { ... },                // object? — 1:1 на пропсы компонента. Нет для композита
      "blocks": [ ... ]                  // object[]? — для композитов: упорядоченные под-компоненты
    }
  ]
}
```

`schemaVersion` — единственное поле корня, которое не описывает контент: оно описывает схему.
Поле секции — ровно одно из `content` или `blocks` (не оба, не ни одного).

### 3.1 Секция = один компонент (`content`)

`content` маппится 1:1 на пропсы. Допустимые ключи — по фактическим пропсам компонентов (перепроверено по коду):

| `component` | Допустимые ключи `content` |
|---|---|
| `HeroSection` | `titleProps`, `image`, `rows[]` |
| `ProblemSection` | `titleProps`, `paragraphTitle`, `paragraph`, `cite{text,source?,avatar?}`, `cards[]` |
| `GoalsSection` | `titleProps`, `cards[]` |
| `ContextSection` | `titleProps`, `image`, `rows[]{title,description}`, `card{variant,title,description}` |
| `PersonaSection` | `titleProps`, `personas[]` |
| `FeatureSection` | `titleProps`, `image`, `metrics[]{type,number,title,description}` |
| `DecisionSection` | `titleProps`, `paragraph`, `tag`, `image`, `noteTitle`, `noteText` |
| `RetrospectiveSection` | `titleProps`, `cards[]` |
| `ResultsSection` | `titleProps`, `results[]{size,title,description}` |
| `ReflectionSection` | `title`, `paragraph`, `header`, `items[]` |
| `GrowthSection` | `titleProps`, `items[]{image,persona}` |
| `QuoteCard` | `leftName`, `leftQuote`, `rightName`, `rightQuote` |
| `RolesTable` | `title`, `description`, `rows[]{role,version,tasks}` |
| `CommonCard` | `variant`, `title`, `description`, `number?: number` |

**Правило `rows`:** ключ массива **всегда называется `rows`**, независимо от компонента. Форма элемента определяется компонентом (`{label,value}` — `RowInfoProject`, `{title,description}` — `ContextSectionRow`, `{role,version,tasks}` — `RolesTableRow`). JSON повторяет реальные пропсы React-компонентов 1:1 без слоя трансляции — ключи не переименовываются (`heroRows`, `contextRows`, `tableRows` и т.п. не используются).

**Правило `number`:** во всех JSON поле `number` имеет только числовой тип (`1`, не `"1"`). Компоненты принимают оба типа, но для единообразия и простоты валидации контент пишется числами.

Вложенные формы (переиспользуют существующие типы пропсов):

- `cards[]`: `{ variant: 'insight'|'risk'|'callout'|'lesson'|'number', title, description?, number?: number }` (CommonCard).
- `metrics[]`: `{ type: 'short'|'long', number?: number, title?, description? }` (MetricCard).
- `personas[]`: `{ title?, description?, icon?, tagText? }` (PersonaCard; `icon` — через ссылку на ассет).
- `rows[]`: `{ label, value }` (RowInfoProject) или `{ title, description }` (ContextSectionRow).
- `results[]`: `{ size: 'L'|'M', title?, description? }` (Results).
- `titleProps`: `{ size: 'L'|'M', children, description?, as? }` (Title).

### 3.2 Композит = `blocks[]`

Для фреймов, собранных из нескольких компонентов (блок №8 «MVP growth»):

```json
{
  "component": "MVPGrowthSection",
  "figmaNode": "1799:0000",
  "blocks": [
    { "component": "PersonaSection", "figmaNode": "1799:0001", "content": { "titleProps": { "size": "M", "children": "Платформа выросла из MVP в единое рабочее пространство" }, "personas": [ ... ] } },
    { "component": "RolesTable",     "figmaNode": "1799:0002", "content": { "title": "Роли в платформе", "description": "...", "rows": [ ... ] } },
    { "component": "CommonCard",     "figmaNode": "1799:0003", "content": { "variant": "risk", "title": "Приоритизировали решение по влиянию на бизнес", "description": "..." } }
  ]
}
```

Правила:
- `component` у композита — стабильное имя фрейма в PascalCase (та же конвенция, что у остальных секций: `MVPGrowthSection`). Имя **сохраняется и не удаляется**: оно описывает назначение блока и становится точным Figma/React-именем, когда для композита будет создан реальный организм.
- `blocks[]` — упорядоченный список; каждый блок — полноценная секция (§3.1 или вложенный композит).
- **Глубина 1** — достаточно для текущих кейсов. Более глубокая вложенность → сигнал извлечь новый организм (правило `design-system.md`).
- Layout композита (обёртки `.mvpSection`, `.gapMapBlock`, `.gapCardSlot`) реализует React (рендерер или новый организм), **не JSON**.

### 3.3 Ссылка на ассет (замена сериализованного ReactNode)

```json
{
  "type": "image",
  "src": "images/<slot>.png",
  "figmaNode": "1799:8882",
  "alt": "Система обработки заявок"
}
```

- `src` — путь **относительно папки кейса** (`content/cases/<slug>/`). Имя файла = имя узла в Figma, формат всегда `.png` (см. §4.2).
- `type` — **обязательный дискриминатор** вида ассета. Сейчас единственное поддерживаемое значение `image`; поле заложено, чтобы resolver был готов к будущим видам ассетов (`icon`, `video`, `svg` и т.д.). `type` определяет форму остальных полей объекта (например, у `icon` вместо `alt` может использоваться ссылка на imageRef из Figma).
- `figmaNode` — узел image-слота в Figma (для сверки «образ ↔ Figma»).
- `alt` — описание содержимого изображения (доступность + семантика).
- Резолвится `AssetResolver` → `<img>`. Если файл отсутствует — рендерится существующий плейсхолдер.
- Обоснование: JSON не может нести React-элементы; это минимально необходимая абстракция.

## 4. Структура папок и изображения

### 4.1 Файловая структура

```
content/
└── cases/
    ├── acquiring/
    │   ├── case.json
    │   └── images/                 ← одна папка на кейс; все файлы .png, имена = как в Figma
    │       ├── <имя слота Figma>.png
    │       └── ...
    └── chat/
        ├── case.json
        └── images/
```

Источник: `architecture.md` уже определяет `content/cases/{acquiring,chat}` — добавляется только папка `images/`. Точный список файлов формируется при экспорте изображений из Figma.

### 4.2 Конвенция имён и формат

**Формат: всегда `.png`.** Изображения импортируются из Figma только в PNG (экспорт из макета → файл `.png`). Никаких webp/svg/прочих форматов в папке `images/`.

**Именование: имя файла = имя узла (слоя) в Figma.** Без самодеятельности:

- Не переименовывать изображения на «свои» имена (`hero.webp`, `context-01` и т.п.).
- Имя файла повторяет имя слоя/узла Figma, из которого экспортируется изображение.
- Если у слоя в Figma нет осмысленного имени — правильное действие — назвать слой в Figma, а не изобретать имя в проекте.
- `figmaNode` в JSON-ссылке связывает файл с конкретным узлом Figma.

Семантика изображения (что на нём) описывается полем `alt` в JSON-ссылке — она не участвует в именовании файла.

### 4.3 Пример заполнения (реальные плейсхолдеры кейса)

> Имена файлов ниже — иллюстративные. По правилу §4.2 реальные имена берутся из Figma (имя слота) и формат — `.png`.

| Слот на странице | Файл (имя = как в Figma) | Ссылка в JSON |
|---|---|---|
| Hero Section image (1216×794) | `images/<slot>.png` | `{ "src": "images/<slot>.png" }` |
| Context Section #1 (pie chart) | `images/<slot>.png` | `{ "src": "images/<slot>.png" }` |
| Feature Section image | `images/<slot>.png` | `{ "src": "images/<slot>.png" }` |
| Decision Section timeline | `images/<slot>.png` | `{ "src": "images/<slot>.png" }` |
| Context Section #2 (architecture) | `images/<slot>.png` | `{ "src": "images/<slot>.png" }` |
| GrowthSection items ×3 | `images/<slot>.png` ×3 | `{ "src": "images/<slot>.png" }` … |

## 5. AI-first workflow

```
Figma
  ↓  1. AI читает дерево узлов кейса (MCP) — имена компонентов и node-id
AI
  ↓  2. AI экспортирует контент (текст, варианты карточек, ссылки на образы)
JSON (case.json)
  ↓  3. AI генерирует case.json: точные component-имена + обязательные figmaNode + конвенция путей
CaseRenderer
  ↓  4. Рендерит без правки компонентов; Storybook-стори показывает кейс сразу
React / Storybook
  ↓  5. Сверка: «сравни ProblemSection с узлом 1799:8882» — по figmaNode, без ручного поиска
Production
```

Новый кейс = новая папка `content/cases/<slug>/` + `case.json` + `images/`. **Кода не требуется**, если набор секций уже покрыт реестром.

## 6. План миграции

1. **`src/entities/case/CaseRenderer.tsx`** — реестр `{ component → React.FC }` + `ContentMap` (тип пропсов на имя) + рекурсивная обработка `blocks`. Unknown → dev-warning.
2. **`content/cases/acquiring/case.json`** — перенос 13 секций 1:1 из `CaseStudyAcquiring.tsx` (значения не меняются); блок №8 → `blocks` (PersonaSection + RolesTable + CommonCard).
3. **`src/lib/content-parser/AssetResolver.tsx`** — резолв `{type:'image', src}` относительно папки кейса; fallback на плейсхолдер.
4. **`CasePage`** — для slug `acquiring` рендерит JSON через `CaseRenderer`; `CaseStudyAcquiring.tsx` остаётся за флагом до подтверждения паритета.
5. **Storybook** — стори `CaseRenderer` с `case.json` (визуальный диф и валидация JSON на старте).
6. **Верификация против Figma** по `figmaNode` (порядок, копирайт, варианты); устранение расхождений.
7. **Удаление** хардкод-страницы после визуального паритета.

## 7. Риски

| Риск | Митигация |
|---|---|
| **Импорт изображений Vite из `content/`** — папка вне `src` | Уточнить на шаге миграции: `public/`-маппинг или импорт через `?url`; резолвер изолирует деталь |
| **Дрейф `figmaNode`** при рефакторинге Figma-файла | Workflow сверки по `figmaNode` ловит расхождение; node-id копируется из дерева, не вручную |
| **Типизированная `ContentMap` растёт** с новыми компонентами | Точечное добавление одной строки на компонент; неизвестное имя → dev-warning |
| **Композиты с нетривиальным layout** (как `.gapCardSlot` width 520) | Ограничение глубины 1; нетривиальный layout → новый организм (правило design-system) |
| **Over-engineering** (схема ради 1 кейса) | Рендерер ~40 строк; схема = существующие типы пропсов; `blocks` — единственное расширение против v1 |
| **Регрессия страницы, свёрстанной под Figma** | Порт 1:1 из текущих JSX-значений; старая страница за флагом; Storybook + визуальный диф |

## 8. Возможные улучшения в будущих версиях

Проблемы, которые не проявятся на одном кейсе, но станут заметны при росте: 10+ кейсов, новые типы секций, новые типы ассетов, автоматическая генерация JSON через AI. Не исправляются сейчас, чтобы не усложнять MVP.

| Триггер | Проблема | Будущее решение |
|---|---|---|
| AI-генерация | Свободная форма `content` требует, чтобы AI знал точные пропсы каждого компонента. Ошибка найдётся только на рендере | Сгенерировать из `ContentMap` JSON-схему или zod-типы и валидировать JSON до рендера (скрипт `validate`) |
| AI-генерация | Ключ `key` свободный — AI может сгенерировать дубликаты или нестабильные значения | Автогенерация `key` из `component` + порядкового индекса; дубликаты → dev-warning |
| AI-генерация | `figmaNode` со значением-заглушкой (`"TBD: ..."`) не является валидным node-id, но формально заполнен | Договорённость: отсутствие node-id = `null`/пропуск + dev-warning, а не текст-заглушка |
| 10+ кейсов | Повтор `figmaNode`: в `acquiring/case.json` два `ContextSection` ссылаются на один узел `1756:15678`, а их изображения — на `1792:16289` | Автоматическая сверка node-id через Figma MCP в workflow; проверка уникальности node-id на кейс |
| Новые ассеты | Форма ассета фиксирована (`src`, `figmaNode`, `alt`); для `icon`/`video`/`svg` поля будут другими | Сделать ассет дискриминированным union по `type` (поле уже заложено, см. §3.3) |
| 10+ кейсов | Длинный текст с `\n\n` и буллетами `•` в JSON-строках хрупок при ручной/AI правке | Рассмотреть массив абзацев `paragraphs[]` или лёгкий markdown для длинных секций |
