## 1. `blocks[]` — принято, остаётся

Подтверждено по `CaseStudyAcquiring.tsx`: блок №8 «MVP growth» — `PersonaSection` + `RolesTable` + `CommonCard` в обёртках (`.mvpSection`, `.gapMapBlock`, `.gapCardSlot`). Без `blocks[]` JSON не смог бы описать композитный кейс. Глубина 1 и правило «глубже → извлекать новый организм» соответствуют `design-system.md`.

**Уточнение (решено):** имя композита переименовано в `MVPGrowthSection` и сохраняется в схеме и JSON. Оно не удаляется: это стабильное имя фрейма в PascalCase, которое станет точным Figma/React-именем при создании реального организма. Node-id фрейма ожидается от владельца.

## 2. Имена изображений — принято с уточнением

Правило `<section>-<N>` (`context-01`, `growth-02`) **позиционное**, а не семантическое по содержимому. Это намеренный компромисс: предсказуемость для AI важнее читаемости имени файла. Семантика контента живёт в поле `alt`, сверяемость с Figma — в `figmaNode`.

**Уточнение в §4.2:** явно записать, что имя файла = идентификатор слота, а не описание содержимого; содержимое описывается полем `alt`. Полностью семантические имена (например, `role-distribution.webp`) отклоняются: риск, что AI начнёт выдумывать имена, разрушает конвенцию.

## 3. Поле `type: "image"` — оставить

Сейчас ассетов только один вид. Но `PersonaCard.icon` (`PersonaCard.tsx:19`) — тоже ReactNode-проп, который по той же логике будет сериализоваться как ассет (`type: 'icon'`, imageRef из Figma). Поле `type` — дешёвый дискриминатор для discriminated-union в `AssetResolver`. Убрать сейчас → добавлять при первом же icon. **Оставить**, дополнить §3.3: `type` — дискриминатор, готовый к будущим видам ассетов (icon и др.).

## 4. Неоднозначные `rows` — оставить, зафиксировать

Проверено по коду — три разные формы одного ключа:

| Компонент | Ключи строки | Молекула |
|---|---|---|
| `HeroSection.tsx:21` | `label`, `value` | `RowInfoProject` |
| `ContextSection.tsx:10` | `title`, `description` | `ContextSectionRow` |
| `RolesTable.tsx:35` | `role`, `version`, `tasks` | `RolesTableRow` |

Ключ одинаковый, потому что проп в каждом компоненте буквально называется `rows` — JSON маппится 1:1. Переименование в JSON (`infoRows`, `contextRows`, `tableRows`) добавит слой трансляции и сломает принцип 1:1. Форму строки определяет `component` в `ContentMap`, а не имя ключа.

**Действие:** примечание в §3.1: «форму `rows` определяет `component`; единый ключ сохраняется ради 1:1-маппинга на пропсы».

## 5. `number` — унифицировать

Подтверждено по коду: `CommonCard.tsx:26` и `MetricCard.tsx:15` — `number?: string | number`. В `case.json` сейчас смесь типов:

- `GoalsSection` — `"number": "1"` … `"4"` (строки, унаследованы из TSX-порта);
- `RetrospectiveSection` — `"number": 1 … 3` (числа);
- `FeatureSection.metrics` — `"number": 1 … 4` (числа).

Компоненты рендерят строки и числа одинаково (`{number}` напрямую; `String(number).padStart(2, '0')` для variant `lesson`), поэтому визуального отличия нет.

**Действие:** в JSON всегда число; в Goals заменить `"1"` → `1`. Схема упрощается до `number?: number`. Правка только контента, React не трогается, визуально идентично.

## 6. `schemaVersion` — добавить

В корне есть `site`, `slug`, `meta`, `sections`, но нет версии схемы. Поле дёшево и разблокирует миграции (например, изменение глубины `blocks` или добавление новых полей).

**Действие:** `"schemaVersion": 2` в корень `case.json` + поле в §3. Значение 2 совпадает с номером ревизии документа (v2).

## Попутное замечание (вне списка из 6)

`docs/design-system.md` (§5, Common Card) устарел: документирует проп `type (5 вариантов)`, а в коде `variant` + `number`. Схема v2 использует `variant` — это верно относительно кода. Рекомендуется синхронизировать `design-system.md` с фактическим API `CommonCard`.
